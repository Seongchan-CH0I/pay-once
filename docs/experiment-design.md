# 실험 설계 — 결제는 왜 두 번 되는가

> 이 문서는 큰 그림만 다룹니다. 하나의 시나리오를 놓고 **환경을 어떻게 두고, 전략을 어떻게 갈아끼울 것인가**가 전부입니다.
> 멱등키 계약·측정 지점·판정 방법 같은 세부는 별도 문서로 분리합니다.

## 1. 시나리오 하나로 고정한다

> **동일한 주문 1건에 대해, 결제 승인 요청이 동시에 N건 들어온다.**

이 프로젝트에서 바꾸는 것은 딱 하나 — **락 전략**뿐입니다. 시나리오, 환경, 도메인, 부하 조건은 처음부터 끝까지 고정합니다.

왜냐하면 비교가 성립해야 하기 때문입니다. 전략마다 다른 상황에서 측정하면 "S4가 S2보다 빠르다"는 말이 전략 차이인지 상황 차이인지 알 수 없게 됩니다.
실험에서 변수를 하나만 움직이는 것과 같은 이유입니다.

현실에서 이 시나리오가 생기는 경로는 세 가지입니다. 셋 다 같은 요청이 겹친다는 점에서 동일합니다.

- 사용자가 결제 버튼을 빠르게 두 번 누름
- 응답이 느려서 클라이언트가 자동 재시도
- 앱과 웹에서 같은 주문을 동시에 결제

## 2. 판정 기준 — 성능보다 정확성이 먼저

모든 실험의 합격·불합격은 아래 세 가지로만 정합니다.

| | 불변식 |
|---|---|
| **I1** | 주문 하나당 성공한 결제는 정확히 1건 |
| **I2** | 차감된 잔액 총액 == 주문금액 × 1 |
| **I3** | 결제 성공 건수 == 잔액 변동 이력 건수 |

**불변식을 깬 전략은 성능을 측정하지 않습니다.** 틀린 답이 빠른 건 의미가 없습니다. 성능 비교는 정확성을 통과한 전략들끼리만 합니다.

## 3. 환경 — 다중 서버가 기본이다

### 전제 — 결제 서버는 여러 대로 뜬다

이 프로젝트가 다중 서버를 기본으로 두는 이유는 트래픽이 아니라 **단일 장애점(SPOF, Single Point of Failure)** 때문입니다.

단일 장애점이란 **그것 하나가 멈추면 시스템 전체가 멈추는 지점**입니다. 서버가 한 대뿐이면 그 서버가 곧 단일 장애점입니다.

#### 한 대뿐일 때 멈추는 경로

배포처럼 계획된 중단만 문제가 아닙니다. 예고 없이 멈추는 경로가 훨씬 많습니다.

| 원인 | 어떻게 멈추는가 |
|---|---|
| 프로세스 종료 | OOM, 처리되지 않은 예외, 배포 스크립트 실수 |
| 호스트 장애 | 하드웨어 고장, 클라우드 AZ 장애, 인스턴스 회수 |
| **Full GC** | 죽지는 않지만 수 초간 stop-the-world. 응답이 없으면 멈춘 것과 같음 |
| 네트워크 단절 | 그 서버로 가는 경로 하나만 끊겨도 전면 중단 |
| 자원 고갈 | 커넥션 풀·스레드 풀 포화 — **S2 실험에서 실제로 보게 될 현상** |

살아 있는데 응답을 못 하는 경우(Full GC, 풀 고갈)가 더 흔하고 더 나쁩니다. 헬스체크는 통과하는데 사용자는 타임아웃을 보기 때문입니다.

#### 결제에서 특히 치명적인 이유

같은 중단이라도 조회 API가 멈추는 것과 결제가 멈추는 것은 무게가 다릅니다.

1. **멈춘 시간이 곧 손실입니다.** 결제는 매출이 발생하는 지점이라 대체 경로가 없습니다.
2. **중간 상태가 남습니다.** 결제는 외부 PG와 요청·응답을 주고받는데, 그 사이에 서버가 죽으면 *PG는 승인했는데 우리 DB에는 기록이 없는* 불일치가 남습니다. 단순히 요청이 실패하는 것과 질이 다릅니다.
3. **복구 직후가 더 위험합니다.** 멈춰 있는 동안 쌓인 클라이언트 재시도가 살아나는 순간 한꺼번에 들어옵니다. **같은 주문에 대한 중복 요청이 폭증하는 이 장면이 바로 이 프로젝트의 시나리오입니다.**

그래서 결제 서버는 트래픽이 적어도 **상시 2대 이상을, 가능하면 서로 다른 AZ에** 둡니다.

#### 무중단 배포는 목적이 아니라 결과다

"무중단 배포를 하려면 2대가 필요하다"는 설명도 맞지만, 근거로는 조금 약합니다. 롤링 배포라면 상시 2대가 필요하지만, 블루-그린은 평시 1대로도 가능하기 때문입니다.

다만 **어떤 방식을 쓰든 결론은 같습니다.** 블루-그린이라도 트래픽을 옮기는 구간에는 구버전과 신버전이 동시에 요청을 받습니다. 그리고 그 두 JVM은 서로의 `synchronized`를 모릅니다. 오히려 더 나쁩니다 — 배포 중에는 응답이 느려져 클라이언트 재시도가 늘어나는, 중복 요청이 가장 많이 생기는 시간대이기 때문입니다.

> 어떤 무중단 배포 방식을 쓰든, **JVM이 2개가 되는 구간은 피할 수 없다.**

#### 2대로도 해결되지 않는 것

주의할 점은 **앱을 2대로 늘려도 단일 장애점이 사라지지 않는다**는 것입니다. 뒤쪽의 DB와 Redis는 여전히 하나씩이고, 그것들이 죽으면 앱이 몇 대든 소용없습니다.

이게 전략 선택에 직접 영향을 줍니다. **S3·S4에서 락을 Redis로 옮기는 것은 단일 장애점을 하나 더 만드는 일입니다.** DB 락(S2)은 이미 있는 장애점을 쓰는 것이고, Redis 락은 없던 장애점을 추가하면서 성능을 얻는 거래입니다. 결함 주입 실험 **F3(Redis 강제 종료)**가 측정하려는 게 정확히 이 거래의 대가입니다.

#### 정리

> 결제 서버는 단일 장애점을 허용할 수 없어 상시 2대 이상으로 운영된다. 따라서 **같은 애플리케이션이 여러 JVM에서 동시에 도는 것이 정상 상태**이고, 단일 서버는 오히려 인위적인 축소판이다.
>
> 그리고 JVM이 여러 개라는 것은, JVM 안에 거는 락이 **전제부터 성립하지 않는다**는 뜻이다.

### E2 — 기본 환경 (다중 서버)

모든 실험은 여기서 수행합니다.

```
                    ┌→ [앱 1] ─┐
[부하 생성기] → [nginx]          ├→ [ DB ] [ Redis ]
                    └→ [앱 2] ─┘
```

같은 애플리케이션 2대를 띄우고 nginx가 요청을 번갈아 보냅니다. **두 앱은 서로의 존재를 모릅니다.**
각자 독립된 프로세스라 메모리가 따로고, 공유하는 것은 뒤쪽의 DB와 Redis뿐입니다.

`docker-compose`로 앱·nginx·DB·Redis를 한 번에 띄웁니다. **개발 단계부터 이 위에서 돌립니다.** "로컬에선 됐는데 컨테이너에선 안 되네" 하는 문제를 없애고, F3(Redis 강제 종료) 같은 실험도 `docker stop` 한 줄로 끝나기 때문입니다.

여기서 벌어지는 일을 풀어 쓰면 이렇습니다. 같은 주문에 대한 요청 두 개가 각각 앱1과 앱2로 갔다고 해봅시다.

- 앱1: "내 안에 아무도 없네" → 잔액 확인 → 결제
- 앱2: "내 안에 아무도 없네" → 잔액 확인 → 결제

둘 다 자기 규칙은 완벽히 지켰는데 결제는 두 번 됐습니다. 서로를 막을 방법이 없기 때문입니다.

그래서 **락을 어디에 두느냐**가 전략의 본질이 됩니다.

| 락을 두는 곳 | 서버 여러 대일 때 | 대가 |
|---|---|---|
| 내 JVM 메모리 | 안 통함 | — |
| 공유 DB | 통함 | 커넥션을 오래 붙잡음 |
| 공유 Redis | 통함 | **단일 장애점이 하나 늘어남** |

### E1 — 대조군 (단일 서버)

```
[부하 생성기] → [앱 1대] → [ DB ] [ Redis ]
```

E1은 나란히 놓인 두 번째 환경이 아닙니다. **S1 하나를 위해서만 존재하는 대조군**입니다.

E1을 아예 없애도 실험은 성립합니다. S1이 E2에서 깨지는 건 그대로 보이니까요. 그런데 그러면 S1이 **허수아비**로 보입니다. "안 되는 걸 갖다 놓고 안 된다고 했네" 같은 인상이 남습니다.

E1에서 통과했다는 대조가 있어야 S1이 *틀린 선택*이 아니라 **조건이 바뀌면 무너지는 선택**이 됩니다. 이 차이가 실험 전체의 톤을 결정합니다 — 전자는 교과서 복습이고, 후자는 한계 검증입니다. 그 대조를 만드는 데 드는 비용이 실험 한 번뿐이라 남겨둘 만합니다.

**S2~S5는 E1에서 돌리지 않습니다.** 어차피 통과할 것이고, 단일 서버 성능 숫자는 이 프로젝트의 질문에 답하지 않습니다.

### 고정할 것

전략을 바꿔도 아래는 항상 같게 둡니다. 이게 흔들리면 측정값을 비교할 수 없습니다.

- 동시 요청 수 N (첫 측정 후 확정)
- DB 커넥션 풀 크기 — **앱이 2대라 앱당 풀 크기를 그대로 두면 DB 입장에서는 커넥션이 2배가 됩니다.** 총량을 맞출지 앱당을 맞출지 정하고 문서에 남깁니다
- 워밍업 후 측정, 매 회차 전 DB 초기화

## 4. 전략을 어떻게 두는가

### 핵심 구조 — 로직은 고정, 락만 교체

전략을 공정하게 비교하려면 **같은 결제 로직에 락만 갈아끼울 수 있어야** 합니다. 전략마다 결제 로직을 따로 짜면 비교가 성립하지 않습니다.

```
        [ PaymentService ]      ← 결제 로직. 어떤 전략에서도 절대 바뀌지 않음
                ↑
        [ 락 전략 인터페이스 ]   ← 여기만 교체
                ↑
   S0 · S1 · S2 · S3 · S4 · S5
```

전략 교체는 설정값 하나로 이뤄지게 합니다. 코드를 고쳐서 전략을 바꾸면, 측정할 때마다 로직이 미묘하게 달라질 위험이 있습니다.

### 전략 6종

각 전략은 앞 전략의 한계를 메우려는 시도입니다. 순서 자체가 이야기가 되도록 배치했습니다.

| | 전략 | 락을 두는 곳 | 이걸로 무엇을 보이는가 |
|---|---|---|---|
| **S0** | 락 없음 | — | 대조군. 문제가 실재함을 증명 |
| **S1** | 애플리케이션 락 (`synchronized`) | JVM 메모리 | JVM 경계를 못 넘는다 |
| **S2** | DB 비관적 락 (`FOR UPDATE`) | 공유 DB | 통하지만 DB가 비용을 낸다 |
| **S3** | Redis 분산락 (직접 구현) | 공유 Redis | 분산락이 실제로 어떻게 도는가 |
| **S4** | Redisson | 공유 Redis | 직접 구현의 낭비를 어떻게 줄이는가 |
| **S5** | 멱등키 + DB 유니크 제약 | — (락이 아님) | 락으로 못 막는 것을 막는다 |

**S0을 빼면 안 됩니다.** 문제가 진짜 있다는 걸 먼저 보여야 나머지 실험에 의미가 생깁니다.

**S5는 락이 아닙니다.** 앞의 다섯 개와 성격이 다릅니다. "동시에 들어온 요청을 줄 세우는 것"이 아니라 "같은 결제는 두 번 저장될 수 없다"는 규칙을 DB에 박아두는 것입니다. 그래서 S5는 S2·S4와 *대체* 관계가 아니라 *병행* 관계입니다.

### 실험 매트릭스

이 표가 실험 결과로 채워질 뼈대입니다.

| | E1 (대조군) | **E2 (기본)** | 이 칸에서 볼 것 |
|---|---|---|---|
| **S0** | — | 깨짐 | 중복 결제 건수 |
| **S1** | **통과** | **깨짐** | ← E1이 존재하는 유일한 이유 |
| **S2** | — | 통과 | 커넥션 점유 시간, 풀 고갈 |
| **S3** | — | 통과 | Redis 명령 수 (대기 비용) |
| **S4** | — | 통과 | S3 대비 명령 수 감소폭 |
| **S5** | — | 통과 | 유니크 제약 위반 처리 비용 |

E1 열의 `—`는 누락이 아니라 **의도적으로 돌리지 않는 칸**입니다.

이 표는 대체로 예상대로 나옵니다. **진짜 볼거리는 다음 절입니다.**

## 5. 결함 주입 — 통과한 전략을 다시 깨뜨린다

위 표에서 "통과"가 찍힌 전략들에 조건을 하나씩 추가해서, 어디까지 버티는지 봅니다. 전부 E2에서 수행합니다.

| | 조건 | 깨지는 전략 | 무엇을 말하는가 |
|---|---|---|---|
| **F1** | 락 해제가 커밋보다 먼저 일어남 | S3, S4 | 락을 걸어도 순서가 틀리면 소용없다 |
| **F2** | 락 임대 시간 초과 (`sleep`으로 GC 흉내) | S3 | 락은 소유가 아니라 임대다 |
| **F3** | Redis 강제 종료 | S3, S4 | 락 저장소가 단일 장애점이 된다 |
| **F4** | 타임아웃 후 클라이언트 재시도 | **S0 ~ S4 전부** | ← 프로젝트의 결론 |

**F4가 이 프로젝트의 답입니다.** 락은 *동시에 들어온 요청*을 줄 세울 뿐, *1초 뒤에 다시 들어온 요청*은 막지 못합니다.
첫 요청이 이미 락을 반납했기 때문에, 두 번째 요청 입장에서는 그냥 평범한 새 요청입니다. 여기서 살아남는 건 S5뿐입니다.

**F3은 3절의 단일 장애점 논의와 직접 이어집니다.** S3·S4가 얻은 성능이 "장애점을 하나 더 만든 대가"였다는 걸 숫자로 보여주는 자리입니다.

제목이 "결제는 왜 두 번 되는가"인 이유가 여기서 나옵니다.

> 답은 **"락을 안 걸어서"가 아니라 "락으로 막을 수 있는 문제가 아니라서"**입니다.
> 락은 경합을 줄이는 최적화이지, 정확성의 보장이 아닙니다.

F1~F3은 의도적으로 만든 조건입니다. 문서에 그렇게 명시합니다. 숨기면 신뢰를 잃고, 밝히면 설계 능력으로 읽힙니다.

## 6. 하지 않을 것

시간을 지키기 위한 방어선입니다.

- 실제 PG사 연동 — mock 서버로 대체하고 타임아웃만 흉내
- 결제 취소·부분 취소·정산
- Redlock 다중 노드 구성 — 문서로만 논의
- DB·Redis 자체의 이중화 — 단일 장애점임을 인지하되 해결은 범위 밖
- 도메인 확장 — **주문·결제·잔액 3개로 고정**

이 프로젝트의 결과물은 결제 기능이 아니라 실험 결과입니다.

## 7. 다음에 정할 것

이 문서에서 일부러 비워둔 항목입니다.

- **멱등키 계약** — 누가 생성하고, 범위가 무엇이고, 첫 요청이 아직 처리 중일 때 두 번째 요청에 무엇을 응답하는가
- **E2 구성 방식** — nginx를 둘지, 부하 생성기가 두 포트로 직접 분산할지
- **측정 지점** — 각 지표를 부하 생성기에서 뽑을지 서버에서 뽑을지
- **불변식 판정 방법** — I1~I3를 무엇이 어떻게 검사하는가
- **동시 요청 수 N** — 첫 측정에서 S0가 안정적으로 깨지는 값으로 확정
